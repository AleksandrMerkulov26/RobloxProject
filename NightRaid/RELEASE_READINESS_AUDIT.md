# NightRaid — аудит готовности к релизу

Дата аудита: 2026-11-20  
Проверенная база: `main` на коммите `5cd5bf1d3b63aaef2e4ebdfd8a320ca8ad074544`.

## Краткий вывод

Проект уже содержит значительный объём игрового кода и несколько автоматических проверок, но по текущему состоянию репозитория его нельзя считать готовым к публичному релизу. Главные риски — жизненный цикл смерти/воскрешения, сохранение профилей при параллельных сессиях, границы доверия RemoteEvents и недостаточное покрытие интеграционными тестами.

Аудит выполнен статически по исходникам и конфигурации GitHub Actions. Он не является подтверждением поведения Roblox Engine или опубликованного experience.

## Блокеры релиза (P0)

### P0-1. Жизненный цикл смерти, нокаута и респавна не имеет единого владельца

Файлы:
- `src/server/init.server.luau` — `loadCharacterForPlayer`, `handlePlayerElimination`, `CharacterAdded`, `HealthChanged`, `Humanoid.Died`.
- `src/server/CoopService.luau` — `DownPlayer`, `RevivePlayer`, bleedout timer.
- `src/server/RoundController.luau` — `ResetPlayerForRound`.

Наблюдения:
- `handlePlayerElimination` всегда планирует `LoadCharacterAsync` через 2 секунды, в том числе после смерти во время рейда.
- `HealthChanged` пытается перевести персонажа в Downed только после достижения порога здоровья, но окончательная смерть обрабатывается отдельным событием `Humanoid.Died`.
- Поведение при первом смертельном уроне, повторном уроне в Downed, истечении bleedout, смерти вне рейда и смерти уже исключённого игрока распределено между несколькими обработчиками.
- В открытом PR #27 предложен ещё один вариант перехвата смерти, но он не подтверждён в Roblox Studio и не должен сливаться как готовое исправление.

Риск: мгновенный респавн вместо окна спасения, повторная обработка смерти, потеря/дублирование лута, неправильный статус игрока в текущем рейде.

Корректировка:
1. Ввести один серверный модуль/контроллер жизненного цикла игрока с явными состояниями: Alive, Downed, Eliminated, Escaped, Lobby.
2. Сделать переходы идемпотентными (повторный вызов одного перехода не должен повторно дропать предметы или выдавать награду).
3. Отделить downed/bleedout от respawn. Респавн в убежище разрешать только после завершения рейда или явного правила для исключённого игрока.
4. Перевести игровые источники урона на общий серверный API урона; не полагаться на попытку отменить уже наступивший `Humanoid.Died`.
5. Добавить unit-тесты переходов и интеграционный сценарий для Roblox Engine.

Критерий готовности: один смертельный удар в рейде переводит игрока в Downed; напарник может поднять его в пределах окна; второй смертельный удар или таймер переводит в Eliminated; респавн не возвращает игрока в текущий рейд; смерть в убежище корректно возвращает его в убежище.

### P0-2. Тестовый серверный скрипт включён в production Rojo-проект

Файл: `default.project.json`.

Наблюдение: production-проект подключал `src/tests` в `ServerScriptService.Tests`. В этой папке находится `TestRunner.server.luau`, который запускает тестовый набор при старте сервера. Следовательно, тестовый раннер попадал в production-сборку.

Исправление в этой ветке: удалено подключение `src/tests` из `default.project.json`. Тестовая сборка `test.project.json` по-прежнему подключает эту папку отдельно.

Критерий готовности: production Rojo build не содержит TestRunner; test Rojo build содержит его.

## Высокий приоритет (P1)

### P1-1. Сохранение профиля не защищено от одновременной сессии на разных серверах

Файл: `src/server/DataService.luau`.

Наблюдение: `playerSaveInProgress` блокирует параллельные записи только внутри одного экземпляра сервера. Межсерверного session lock по UserId/JobId в проверенном коде не обнаружено. `UpdateAsync` записывает целиком сформированный профиль, а не объединяет независимые изменения.

Риск: две активные сессии одного игрока могут перезаписать прогресс друг друга.

Корректировка: внедрить межсерверную блокировку профиля с lease/TTL и проверкой владельца при записи; корректно освобождать блокировку при выходе и закрытии сервера. Добавить тесты на повторное подключение и конфликт сессий.

### P1-2. Не все RemoteEvent имеют одинаково строгую проверку состояния игрока

Файл: `src/server/init.server.luau`.

Наблюдения:
- `ToggleCrouch` проверяет тип аргумента и Downed, но не проверяет фазу, Eliminated и живого персонажа перед изменением атрибута/скорости.
- `RadioPing` проверяет фазу, тип/конечность координат и cooldown, но не проверяет, что отправитель жив, не исключён и не находится в Downed; координата не ограничена разумной дистанцией от игрока.
- `BuyHideoutDeco` проверяет ID и баланс, но не требует LobbyPhase и нахождения игрока у станции убежища.
- `RevivePlayer` на main по-прежнему использует отдельную проверку в обработчике RemoteEvent и другую логику в `CoopService`; проверки должны быть централизованы.

Корректировка: единый helper проверки состояния игрока и контекста действия; для каждого RemoteEvent — allowlist фаз, живой персонаж, статус Eliminated/Downed, cooldown, типы/диапазоны аргументов и серверная проверка расстояния/линии видимости там, где требуется.

### P1-3. Сохранение данных при выходе и закрытии сервера требует усиления

Файл: `src/server/DataService.luau`, `src/server/init.server.luau`.

Наблюдение: сохранение запускается при PlayerRemoving, периодически и при BindToClose. Внутрисерверный флаг сериализует записи, однако ожидание в цикле без верхнего лимита может зависнуть при незавершённой операции; обработка аварийного завершения и подтверждение последнего успешного сохранения требуют отдельной проверки.

Корректировка: ограниченные ожидания, гарантированное снятие флага через защищённый шаблон, логирование времени/результата сохранения, тесты на сбой DataStore и shutdown.

### P1-4. Еженедельный лидерборд фактически не имеет недельной ротации

Файл: `src/server/LeaderboardService.luau`.

Наблюдение: используется один OrderedDataStore `WeeklyCashLeaderboard_v1`; ключ игрока — UserId, запись через SetAsync. В коде не обнаружена смена имени хранилища/ключа по неделе или сброс сезона.

Риск: название и маркетинговое описание обещают недельный рейтинг, а реализация хранит накопительное значение без недельной ротации.

Корректировка: либо реализовать ключ сезона на основе UTC-недели и политику rollover, либо переименовать функцию/описание в lifetime leaderboard.

### P1-5. Автоматические тесты не покрывают критические серверные интеграции

Файл: `.github/workflows/night-raid-ci.yml`.

Текущий CI выполняет Selene, две Rojo-сборки и Lune-тесты чистых правил. Он не запускает Roblox Engine и не тестирует DataStore, RemoteEvents, NPC, физику, ProximityPrompt, Character lifecycle и многопользовательские сценарии.

Корректировка: сохранить быстрый CI, добавить отдельный checklist/автоматизированные Studio smoke tests и не обозначать проект как полностью протестированный только по успешному CI.

## Средний приоритет (P2)

### P2-1. Маркетинговые обещания не сопоставлены с подтверждённой реализацией

Файлы: `README.md`, `STORE_LISTING.md`.

В описаниях заявлены адаптивная охрана, тактический replay, недельный лидерборд, кооперативное воскрешение и ряд других функций. Наличие модуля или названия функции не доказывает корректную работу полного пользовательского сценария.

Корректировка: перед публикацией составить матрицу Feature → Code → Runtime evidence и убрать/смягчить неподтверждённые обещания.

### P2-2. Производительность и визуальная готовность карт не подтверждены

Файлы: `src/server/MapBuilder.luau`, `src/shared/MapConfigs.luau`, `src/server/HideoutBuilder.luau`.

Карты и убежища в значительной степени создаются программно из Part. Статический аудит не подтверждает целевой визуальный уровень, FPS, сетевую нагрузку и производительность слабых устройств.

Корректировка: ограниченный perf-профиль на целевом сервере, проверка плотности деталей/света/частиц, визуальная проверка всех карт. Мобильную адаптацию можно оставить отдельным этапом, но базовый UX должен быть пригоден для игры.

## Release gate

Публичный релиз разрешать только после:
- отсутствия известных P0 дефектов;
- успешного production build без тестового раннера;
- успешного CI на финальном коммите;
- подтверждённого сохранения/загрузки профиля и защиты от одновременных сессий;
- прохождения сценариев: новый игрок, рейд, лут, эвакуация, смерть, нокаут/воскрешение, исключение, выход во время рейда, повторное подключение;
- проверки всех заявленных в Store Listing ключевых функций;
- проверки опубликованного Roblox experience с включёнными production DataStore.

## Ограничения аудита

Это статический аудит репозитория. Он не подтверждает runtime-поведение Roblox Engine, доступность ассетов, права на аудио, фактическую работу всех карт/NPC/эффектов, сетевую производительность или корректность production DataStore. Эти пункты отмечены как release verification, а не объявлены выполненными.
